# Verified Track Record & Calibration Engine\n\n## Objective\n\nSolpient must be able to show what it predicted, what later happened, and how well calibrated those forecasts were without rewriting history or overstating skill.\n\nThe engine is built on the existing Phase 1 prediction ledger:\n\n- locked prediction snapshots\n- immutable prediction outcomes\n- append-only realized outcomes with correction/supersession semantics\n- versioned prediction scores\n\nIt does not alter those records. It recomputes a consistent Track Record V1 methodology from the raw locked forecast and authoritative realized outcome.\n\n## Why recompute from raw forecast/outcome\n\nLegacy evaluators used more than one percentage-error convention. Track Record V1 therefore does not aggregate stored legacy percentage_error blindly. Numeric error is recomputed consistently as absolute error divided by absolute actual value when actual is non-zero.\n\n## Verified outcome definition\n\nA row is counted as verified only when:\n\n1. the prediction snapshot was locked;\n2. an authoritative realized outcome exists;\n3. the realized row contains an actual value or text;\n4. the realized row has source lineage through source_note or source_url.\n\nRows can instead be classified as unresolved, weak lineage, or unverified snapshot. Those rows remain visible in coverage counts but do not inflate accuracy statistics.\n\n## Correction handling\n\nRealized outcomes are append-only. If a correction supersedes an earlier realized row, the materializer chooses the current leaf of the supersession chain for calibration. The original row remains preserved.\n\n## Metrics\n\n### Numeric forecasts\n\n- MAE\n- RMSE\n- mean signed error / bias\n- MAPE using actual as denominator\n- median absolute percentage error\n- symmetric MAPE\n- prediction-interval coverage when explicit low/high bounds exist\n- mean interval width\n\n### Directional forecasts\n\nDirection accuracy is calculated only for genuinely directional targets such as price return, benchmark-relative return, probability classifications, or explicit outperform/underperform calls.\n\nPositive level forecasts such as revenue are not treated as automatically directionally correct.\n\n### Probability forecasts\n\n- Brier score\n- log loss\n- classification accuracy at the declared 50% decision threshold\n- 20-percentage-point reliability buckets\n- expected calibration error\n\n### Snapshot confidence\n\nPrediction-snapshot confidence is calibrated only against outcomes for which directional correctness is meaningful. This prevents level forecasts from artificially improving confidence calibration.\n\n### Benchmark-relative results\n\n- mean excess return\n- median excess return\n- benchmark win rate\n\nThese are forecast-outcome statistics, not a simulated portfolio return or alpha claim.\n\n## Sample grades\n\n- fewer than 5 verified outcomes: Insufficient\n- 5–19: Emerging\n- 20–49: Meaningful\n- 50+: Robust\n\nMetrics may be displayed at every sample size, but Solpient must not claim forecasting skill from Insufficient or Emerging history.\n\n## Evaluation scopes\n\nEach immutable evaluation run stores separate aggregate snapshots for:\n\n- global history\n- company\n- model version\n- forecast horizon\n- outcome type\n- metric key\n\nThis allows later questions such as whether a model is well calibrated overall but weak on valuation forecasts or six-month horizons.\n\n## Historical integrity\n\nThe aggregate track-record tables are append-only. A run hashes the exact forecast/outcome inputs it evaluated. If the same input hash already exists, the materializer writes zero duplicate evaluation records.\n\nChanges in realized outcomes, corrections, or new matured forecasts create a new evaluation run rather than editing an old one.\n\n## Current live-state expectation\n\nAt implementation time the live ledger contained one locked prediction snapshot with five forecast outcomes and no realized outcomes. The engine should therefore report Insufficient verified history and make no forecasting-skill claim until outcomes mature.\n\n## Phase 2 isolation\n\nThis engine intentionally does not modify evidence provenance, temporal research readers, publication, or PredictionHistory. Phase 2 can later strengthen realized-outcome source verification without changing historical Track Record V1 runs; that should be introduced under a new methodology version if scoring semantics change.
