# Methodology Registry / Model Governance V1\n\n## Purpose\n\nSolpient now has multiple independent analytical methodologies. Historical integrity requires more than immutable data: it also requires immutable definitions of **how** scores, valuations, readiness states, forecasts, and screening decisions were produced.\n\nThe registry answers:\n\n- What methodology/version produced this output?\n- What inputs, weights, thresholds, assumptions, and dependencies did that version use?\n- What limitations were known at the time?\n- What validation evidence existed before activation?\n- What methodology did it replace?\n- Was it active, candidate, blocked, deprecated, superseded, or retired?\n\n## Core rule\n\nMaterial methodology changes create a **new version**.\n\nSolpient must not silently edit an active methodology's weights, thresholds, assumptions, input contract, output contract, dependencies, or decision impacts while continuing to call it the same version.\n\n## Immutable records\n\nThree append-only ledgers are used:\n\n1. `methodology_definitions` — immutable version manifests.\n2. `methodology_lifecycle_events` — immutable state transitions.\n3. `methodology_validation_runs` — immutable validation evidence.\n\nCurrent lifecycle state is derived from events rather than stored as an editable status column.\n\n## Lifecycle\n\nSupported states:\n\n- Registered\n- Candidate\n- Validated\n- Active\n- Blocked\n- Deprecated\n- Superseded\n- Retired\n\nNormal future flow:\n\n`Registered → Candidate → Validated → Active → Deprecated/Superseded → Retired`\n\nBlocked versions can return to Candidate/Validated/Active only after the underlying issue is resolved and new validation evidence is appended.\n\n## Validation gates\n\nEvery future methodology requires:\n\n- unit tests\n- production build\n\nAdditional requirements are added by impact:\n\n- database change → DB invariant test\n- publication or historical-interpretation change → historical-integrity validation\n- capital-decision or Critical risk → manual review\n- valuation/ranking/prediction/calibration/screening → methodology regression test\n\nCritical-risk methodologies cannot satisfy a required activation gate through a waiver.\n\n## Legacy bootstrap\n\nExisting production methodologies predate Registry V1. They can be imported once as `legacy_bootstrap=true` and marked Active so the registry starts from the real current system.\n\nThis **does not** imply retroactive Registry V1 certification.\n\nThe dashboard explicitly labels those versions `Legacy baseline` and shows that no retroactive validation evidence is implied.\n\n## Initial active baseline\n\nRegistry V1 initially describes methodologies already verifiably present on current `main`:\n\n- Historical Integrity V1\n- Research Composer V2\n- Historical Context V2 Provenance\n- Data Coverage V2\n- Decision Ranking V1\n- Decision Readiness V1\n\nUnmerged work such as Valuation V3, Verified Track Record, Decision Readiness Repair, and Universe Screening is intentionally **not** marked Active merely because a development branch exists.\n\n## Change classification\n\n`diffMethodologies()` classifies changes as:\n\n- Patch — naming, owner, documentation/change-summary only.\n- Minor — source-file or known-limitation changes.\n- Major — input/output contracts, weights, thresholds, assumptions, dependencies, or decision impacts.\n\nMinor and Major changes require a new methodology version.\n\n## Catalog drift\n\n`scripts/check-methodology-drift.mjs` verifies that each catalog entry has real declared source files and that its version string appears in at least one of them.\n\nThis prevents the governance catalog from becoming an aspirational document that no longer matches implementation.\n\n## Administrative commands\n\n### Validate/bootstrap catalog\n\n`node scripts/register-methodologies.mjs --dry-run`\n\nAfter the migration is intentionally deployed, running the command without `--dry-run` inserts missing immutable definitions. Existing production methods with `legacy_bootstrap=true` receive explicit Registered and legacy Active events.\n\n### Record validation evidence\n\n`node scripts/govern-methodology.mjs --key=decision_ranking --version=decision-ranking-v2 --validation-type=unit_tests --validation-status=pass --evidence-ref=ci://run/123`\n\n### Lifecycle transition\n\n`node scripts/govern-methodology.mjs --key=decision_ranking --version=decision-ranking-v2 --event=candidate --reason="Ready for validation"`\n\nActivation is rejected unless every required validation gate is satisfied.\n\n## Security\n\nThe registry is internal-only:\n\n- RLS enabled on all tables.\n- `anon` and `authenticated` have no table grants.\n- `service_role` receives SELECT/INSERT only.\n- UPDATE, DELETE and TRUNCATE are revoked.\n- Phase 1 append-only triggers provide an additional database-level guard.\n\n## Phase 2 isolation\n\nRegistry V1 does not change provenance, temporal readers, publication, or research composition. Phase 2 can later register its final methodology version after its implementation stabilizes. That version should be added as a **new catalog entry**, not by changing historical methodology definitions.
